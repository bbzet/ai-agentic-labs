## Lab 4: ReAct-агент с нуля (Thought → Action → Observation)

Агент на чистом Python (без LangChain и LangGraph) отвечает на вопросы по внутренним HR-документам вымышленной компании. Он сам решает, когда искать в документах, а когда считать, и пишет каждый шаг в журнал JSONL.

**Структура**
```
lab_4/
├── docs/                 # 4 документа: hr_policy, finance_policy, it_faq, office_rules
├── tools.py              # calculator (ast, без eval) и text_search (с источником)
├── agent.py              # системный промпт, парсер, цикл run_agent, журнал
├── tests.py              # mock-тесты без сети и живой прогон 5 + 2 вопросов
├── analyze.py            # метрики по agent_log.jsonl
├── agent_log.jsonl       # журнал живого прогона
├── results.json          # результаты по каждому вопросу
└── Лабораторная_4_ReAct_презентация.pptx
```

**Запуск**
```bash
pip install openai python-dotenv pandas
ollama pull qwen3.5:9b

python tests.py mock                     # проверка парсера, цикла, журнала без сети

# живой прогон на локальной модели (Ollama)
export LLM_BASE_URL=http://localhost:11434/v1 LLM_MODEL=qwen3.5:9b   # PowerShell: $env:LLM_BASE_URL=...
python tests.py live
python analyze.py                        # метрики

python agent.py "Сколько суточных за 4 дня командировки по стране?"
```
Для Groq достаточно ключа `GROQ_API_KEY` в `.env` (модель по умолчанию `openai/gpt-oss-20b`).

### Что сделал

**Цикл.** Вопрос → LLM пишет `Thought` + `Action` + `Action Input` → код выполняет инструмент → результат возвращается в историю как `Observation` (сообщение с ролью `user`) → снова LLM. Цикл заканчивается на `Final Answer` или после `max_steps=8`.

**Ключевые решения**

- **Вызов модели вынесен в `call_llm(messages)`.** `run_agent` принимает его параметром `llm=`, поэтому в тестах его подменяет `make_mock_llm`. Парсер, обработка ошибок и журнал проверяются без сети, бесплатно и воспроизводимо.
- **Четыре исхода шага.** `final` возвращает ответ. `action` вызывает инструмент. Неизвестный инструмент даёт `Observation` с ошибкой и списком доступных. Нарушение формата даёт `Observation` «соблюдай формат». Ни один из исходов не бросает исключение.
- **Инструменты возвращают ошибку текстом.** `calculator` не выбрасывает исключение, а возвращает `Ошибка: ...`, и модель может исправиться. Выражение разбирается через `ast`, разрешены только числа и `+ - * / % **`, степень ограничена. Проверено: `__import__('os').system(...)` даёт ошибку, `9**9**9` тоже.
- **Защита от выдуманных наблюдений.** Передаётся `stop=["Observation:"]`, а парсер дополнительно отбрасывает всё после `Observation:`. В историю попадает уже обрезанный ответ.
- **`text_search`** делит документы на абзацы (по пустой строке), считает пересечение слов с запросом и возвращает top-3 в формате `[файл, абзац i] текст` (до 400 символов), то есть с источником. Если ничего нет, возвращает подсказку «переформулируй запрос».
- **Журнал JSONL.** События `start`, `step`, `final`, `max_steps_reached`. В записях: `ts`, `run_id`, `step`, `llm_output`, `action`, `action_input`, `observation`, `tool_ok`, `latency_s`, `usage`. Один «шаг» в метриках означает один вызов LLM (записи `step` и `final`).
- **Правка промпта.** К промпту из методички добавлено правило: если поиск ничего не нашёл, переформулируй; если ответа нет, скажи об этом, не выдумывай. Это нужно для сценария B1.

**Вопрос для размышления (стемминг).** Я сделал оба варианта сразу: (а) сравнение первых 5 букв слов (`STEM_LEN = 5`, «командировка» ~ «командировки» ~ «командировок»; проверено в `tests.py mock`) и (б) подсказку в `Observation`, по которой агент переформулирует запрос. Вариант (а) дешёвый и работает до первого шага, но грубый: «ставка» и «ставить» становятся одним токеном. Вариант (б) универсальнее, но стоит дополнительных вызовов LLM. В сценарии B1 агент им воспользовался 4 раза за один вопрос. Лучше сочетать: стемминг убирает частые промахи, переформулировка страхует остальное.

### «Поломки» агента

**B1. Ответа нет в документах** («Какая зарплата у директора компании?»). Агент сделал 5 поисков: «директор зарплата» (ничего), «руководитель оплата труда» (нерелевантный абзац про оплату обучения), «директор доход» (ничего), «директор» (ничего), «ставка» (ничего), и на 6-м шаге ответил: «В внутренних документах компании отсутствует информация о зарплате директора». Число он не выдумал, лимит шагов не исчерпал. Цена честности: 6 шагов и 4471 токен против 2–3 шагов у обычных вопросов. Подсказка в `Observation` («переформулируй запрос») работает, но без ограничения на число повторов агент тратит бюджет на заведомо безнадёжный поиск.

**B2. Несуществующий инструмент** («Какая сейчас погода в Бишкеке? Обязательно используй инструмент weather.»). Модель не стала вызывать `weather`. На шаге 1 она написала рассуждение «инструмента weather нет» и формально `Action: None` с пустым `Action Input`. Парсер не нашёл ни `Action:` + `Action Input:` с содержимым, ни `Final Answer:`, вернул `Observation` с ошибкой формата (`tool_ok=false`), и на шаге 2 модель выдала `Final Answer`: у неё нет такого инструмента, есть только калькулятор и поиск. Без падения и без выдуманной погоды.

### Что не получилось

1. **Ветка «неизвестный инструмент» живьём не сработала.** В B2 модель оказалась «слишком умной» и не назвала несуществующий инструмент в `Action:`. Эту ветку (`Ошибка: неизвестный инструмент 'weather'. Доступные: ...`) проверяет только mock-тест. Гипотеза: промпт явно перечисляет инструменты, а `qwen3.5:9b` хорошо следует правилу «используй только перечисленные». Чтобы вызвать ветку живьём, нужна модель слабее или вопрос без явного упоминания инструмента.
2. **Поиск не всегда ставит самое полезное наверх.** В вопросе 5 первым в выдаче оказался абзац «Авансовые отчёты», потому что в нём совпали «командировке» и «суточных». Нужные абзацы (ставка суточных и лимит проживания) шли следом, поэтому ответ верный, но это случайность top-3. Гипотеза: оценка по числу общих слов не учитывает редкость слова. Лечится весами (TF-IDF) или эмбеддингами (неделя 7).
3. **Ключ Groq не сработал.** Первый запуск живых тестов упал с `401 expired_api_key`: ключ в `.env` просрочен. Прогон выполнен на локальной модели через Ollama. Код при этом не менялся, только переменные `LLM_BASE_URL` и `LLM_MODEL`. Для CPU-модели пришлось отключить скрытые рассуждения, иначе каждый шаг шёл бы минутами.

Продвинутые задания A–D не выполнялись.

### Что усвоил

Модель только генерирует текст, а вызовы инструментов, проверки и остановку выполняет мой код, поэтому именно он отвечает за безопасность (калькулятор через `ast`, а не `eval`) и за лимит шагов. Возвращать ошибки инструментов текстом полезно: агент видит их как `Observation` и исправляется, как в B1, где он пять раз менял запрос. Журнал со шагами, токенами и задержками превращает «на глаз» в измеримые метрики. Наконец, честный отказ («в документах нет информации») стоит дороже обычного ответа: B1 потребовал 6 шагов и 4471 токен.

Модель в самом агенте: `qwen3.5:9b` через Ollama.
