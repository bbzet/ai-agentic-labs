## Lab 7: RAG — как нарезка документов влияет на поиск

Лаба «облегчённая»: база знаний вымышленной компании ОсОО «АлаТех Солюшнс» (532 документа, 10 вопросов с эталонами). Сравниваются размеры чанков, считаются Hit@1 / Hit@5 / MRR, затем LLM отвечает на вопросы по найденному контексту. Ноутбук из Colab перенесён в локальные скрипты.

**Структура**
```
lab_7/
├── kb.py                  # генератор базы знаний (seed=7, воспроизводим) -> kb_alatech/
├── rag.py                 # make_chunks, build_index (ChromaDB), retrieve, evaluate, is_relevant
├── experiment.py          # шаги 3, 5, 6: 5 конфигураций, метрики, top-5 для q03/q09, график
├── answers.py             # шаг 7: ответы LLM по лучшей конфигурации
├── experiment.json        # таблица 1
├── ranks.json             # позиция правильного чанка по каждому вопросу и конфигурации
├── retrieval_metrics.png  # график Hit@1 / Hit@5 / MRR для 200 / 500 / 1000
├── answers_500_75.json    # ответы модели, конфигурация 500/75
├── answers_500_150.json   # ответы модели, конфигурация 500/150
└── *_output.txt           # полный вывод запусков
```

**Запуск**
```bash
pip install chromadb sentence-transformers langchain-text-splitters langchain-ollama groq python-dotenv pandas matplotlib

python kb.py                  # создать kb_alatech/ (532 документа)
python experiment.py          # метрики, top-5, график
python answers.py 500/75      # ответы LLM (по умолчанию Ollama, qwen3.5:9b)
python answers.py 500/150

LLM_PROVIDER=groq python answers.py 500/75    # Groq, нужен действующий GROQ_API_KEY
```
В PowerShell: `$env:LLM_PROVIDER="groq"`. Эмбеддинги: `paraphrase-multilingual-MiniLM-L12-v2`, индекс ChromaDB с косинусной метрикой, `RecursiveCharacterTextSplitter`, top-5.

### Что именно нашёл поиск (шаг 6)

**q03 «Какие суточные положены при командировке в Алматы?»** не найден ни в одной конфигурации. Нужный чанк существует (в 500/75 это `POL-FIN-001#6`, фраза «При командировках в Казахстан и Узбекистан суточные составляют 45 долларов США»), но в тексте нет слова «Алматы», есть «Казахстан». Эмбеддинг вопроса ближе к чанкам, где просто много «отпуска/командировки»:
- 200/30: top-5 целиком состоит из приказов «О графике отпусков» (ORD-103, ORD-031, ...);
- 500/75: филлер-фразы из положений (POL-HR-002, POL-ADM-001, POL-ADM-002, POL-HR-004) и тикет «Вопрос по отпуску»;
- 1000/150: пять тикетов «Вопрос по отпуску» (HD-11624, HD-12114, ...), расстояния почти одинаковые (0.469–0.471).

Это отказ именно поиска: нужен вывод «Алматы → Казахстан», а модель эмбеддингов его не делает.

**q09 «Кто назначен ответственным по приказу №87-к?»** `ORD-087` находится на 3-м месте в 500/75, 500/150, 500/0 и 1000/150 и не находится в 200/30. Первые места занимают приказы «О командировании» (ORD-068, ORD-108, ORD-116, ...) с расстояниями 0.285–0.326 против 0.324 у нужного. Приказы одинаковы по шаблону и отличаются номером и фамилией, а эмбеддинги почти не различают числа. В 200/30 top-5 тоже состоит только из приказов «О командировании», а нужный приказ в него не попал.

### Ответы на вопросы

**1. Лучшая конфигурация по MRR и почему.** Из трёх обязательных лучшая 500/75 (MRR 0.592, Hit@5 = 0.8). Среди всех, включая бонус, — 500/150 (MRR 0.617, Hit@1 = 0.5, Hit@5 = 0.8). Разница 0.025 равна одной позиции в одном из десяти вопросов, поэтому разницу между 500/75 и 500/150 я бы не считал значимой.

Мелкие чанки (200, 1320 штук) хуже по Hit@5 (0.6): положение режется на куски по 150–200 символов, где фраза-ответ отделяется от контекста, а в чанк попадают отдельные «филлер»-предложения, которые похожи друг на друга и забивают top-5. q07 и q09 при 200/30 не находятся совсем. Короткие документы (тикеты, приказы, FAQ, 150–300 символов) при этом остаются одним чанком, поэтому приказов в выдаче много.
Крупные чанки (1000, 629 штук) дают худший MRR 0.353 и Hit@1 = 0.3: вектор одного чанка усредняет несколько абзацев, конкретный факт (45 долларов, 14 дней) растворяется, и чанки-«темы» вроде тикетов про отпуск оказываются ближе. q01, q02, q07 не найдены совсем, q04 только на 5-м месте. Кроме того, 5 чанков по 1000 символов дороже по токенам в промпте.

**2. Точность ответов лучшей конфигурации.** 500/75: 7.5 / 10 (75%). Ошибки совпадают с колонкой «найден ли нужный чанк» для q03 и q05 (оба «нет», оба 0). Но совпадение неполное: q04 найден (да), а ответ получил 0.5. Причина в границе чанка: в 500/75 фраза «Право на удалённую работу возникает после успешного прохождения испытательного срока» осталась в соседнем чанке, который в top-5 не попал, а найденный чанк содержит только «не более 2 рабочих дней в неделю». Метрика Hit проверяет только gold_snippet, но не то, что в контексте есть вся информация для ответа. Модель при пустом контексте честно отвечала «В документах нет информации», выдумок в 10 ответах не было.

**3. Разбор ошибки: q03 (суточные в Алматы).** Это ошибка **поиска**, не модели. Нужный чанк `POL-FIN-001#6` не попал в top-5 ни в одной конфигурации (по q03 пустые ячейки во всей таблице позиций), модель получила чужой контекст и правильно ответила «В документах нет информации». Причина — лексический разрыв: в вопросе «Алматы», в документе «Казахстан и Узбекистан». Чисто семантический поиск на MiniLM этого не связывает. Улучшения: (а) гибридный поиск (BM25 + эмбеддинги), (б) переписывание запроса LLM («Алматы» → «Казахстан, суточные, командировка»), (в) метаданные и фильтр по типу документа (`type=policy`): тикеты и приказы вообще не должны конкурировать с положением, (г) более сильная модель эмбеддингов (multilingual-e5, bge-m3), (д) reranker поверх top-20. По q05 (пароль) причина того же рода: top-5 занимают 5 тикетов «Сброс пароля», они короче и ближе к слову «пароль», чем абзац из политики безопасности.

Подсказка из задания про «положения об отпусках» относится к q01: в базе две редакции (2026 и 2023, утратившая силу), и в 500/75 первые два результата — заголовок «2. Продолжительность отпуска» из обеих редакций (20 и 24 дня) с одинаковым расстоянием 0.321. Если бы ответ строился по первому, модель могла бы назвать 20 дней. Помогает метаданные-фильтр по актуальности или удаление утративших силу документов из индекса.

### Бонус: своя конфигурация

Добавлены `(500, 0)` и `(500, 150)`. Без перекрытия (500/0) MRR падает до 0.525 против 0.592 у 500/75: отличается один вопрос, q02 (позиция 3 вместо 1). Увеличение overlap до 150 (30%) даёт MRR 0.617: q01 и q07 поднимаются на 1-е место (у 500/75 они на 4-м и 3-м), но q02 уходит на 3-е, а q04 на 2-е. Цена — 717 чанков вместо 697 и больше дублей в выдаче (в q02 в контекст попала утратившая силу редакция). Вывод: overlap влияет на отдельные вопросы в обе стороны, и по 10 вопросам однозначно сказать, что 150 лучше 75, нельзя.

### Что не получилось и ограничения

1. **Groq не использован:** ключ в `.env` просрочен (`401 expired_api_key`), поэтому шаг 7 выполнен на локальной `qwen3.5:9b` (Ollama, `reasoning=False`, `temperature=0`). Ветка `LLM_PROVIDER=groq` написана, но успешным ответом модели не проверена.
2. **Выборка маленькая:** 10 вопросов, один вопрос даёт 0.1 в Hit@k, а смена позиции правильного чанка на одном вопросе сдвигает MRR на несколько сотых. Различия 0.025–0.07 между конфигурациями 500/0, 500/75, 500/150 находятся на уровне шума; надёжно отличается только 1000/150 (MRR 0.353).
3. **Метрика Hit** определяется по подстроке `gold_snippets`, то есть проверяет наличие фразы в чанке, а не достаточность контекста для ответа (случай q04).
4. **Оценки ответов выставлены вручную** (мной по эталонам), строгость — на усмотрение проверяющего; отдельного LLM-судьи нет.
5. **Сравнение конфигураций детерминировано** (seed генератора 7, `temperature=0`), но на другой версии модели эмбеддингов или splitter значения могут слегка отличаться.

### Что усвоил

1. Размер чанка нужно подбирать под данные: у документов разной длины (положения по 4.6 тыс. символов и тикеты по 240) один `chunk_size` работает по-разному. Короткие документы чанкинг вообще не затрагивает.
2. Слишком мелкие чанки теряют контекст, слишком крупные размывают вектор; на этих данных оптимум около 500 символов.
3. Overlap защищает от потери условия на границе чанка (q04), но создаёт дубли. Ноль overlap — худший вариант на этих данных.
4. Чисто семантический поиск плохо справляется с точными значениями (номер приказа, «Алматы» против «Казахстан»): нужен гибридный поиск, метаданные и rerank.
5. Считать метрики отдельно для поиска и для ответа необходимо: так видно, где ошибка (поиск или модель). Строгий промпт «только по контексту» превращает ошибки поиска в «нет информации», а не в галлюцинации.
